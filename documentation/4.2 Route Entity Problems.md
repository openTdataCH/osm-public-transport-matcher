# E4.2 Route entity problems

> [!NOTE]
> **Planned, not implemented.** The engine builds line families, itineraries, stop calls and route matches ([E3](3.%20Routes.md)), but it does not yet derive problems from them. Only stop problems are emitted today.

Route entity problems would describe a route as a whole, independently of its individual stops. They answer: *does this route exist on both sides, and are its attributes the same?*

## Unmatched route

A line family exists in one dataset but has no counterpart in the other:

- **Source only:** a GTFS route has no matched OSM route relation or route master.
- **OSM only:** an OSM route has no matched GTFS route.

Proposed priorities:

| Priority | Condition |
|---|---|
| **P1** | The route has more than 20 stops |
| **P2** | 5 to 20 stops |
| **P3** | Fewer than 5 stops |

Example: GTFS lists bus 72 with 25 stops, but OSM has no route relation for it.

## Route attribute mismatch

A family is matched, but its attributes disagree. A detection could:

1. take the matched families from `line_family_matches`;
2. compare the public route name and number with the OSM `ref` and `name`;
3. compare the GTFS `route_type` with the OSM `route` mode, through an explicit mode mapping.

It could emit a `route_metadata_mismatch` problem for mode, name and number disagreements. Comparing `network` and `operator` would be a later step.

Today the family matcher compares route identifiers and, for the families still unmatched, mode, line number and stops ([E3.2](3.2%20Route-Route%20Matching.md#step-2-match-the-families)); it records its `match_method` but no disagreement, and no route-level rule package or problem storage exists yet.

## Outdated route identifier

A family matched by line number and stops (`line_number_and_stops`, [E3.2](3.2%20Route-Route%20Matching.md#by-line-number-and-stops)) has no usable `gtfs:route_id`: the tag is missing, outdated or names another line. The match tells which identifier the OSM line should carry, the source family's `route_id`. A problem could list the OSM line, its tag and that identifier; once a mapper updates the tag, the next run matches the line by identifier.
