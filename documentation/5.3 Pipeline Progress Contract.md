# E5.3 Pipeline Progress Contract

The command-line pipeline exposes operational progress as a small, versioned JSON contract. It is deliberately separate from the result-bundle schema: progress is transient orchestration state, while a result bundle is a durable matching result.

## Ownership and source of truth

`src/transport_matcher/progress.py` is the canonical catalog for engine-owned public substages. Each entry has a stable ID, parent phase, display label, description, order and progress kind. Internal timing spans can remain more detailed and may change without affecting consumers.

The engine emits the selected run plan once as `pipeline_plan`, then emits `stage_started`, `stage_progress`, `stage_finished`, `stage_failed` or `stage_outcome` events. Every public event carries `progress_schema_version: 1`. Labels are presentation metadata; consumers use `stage_id` as identity.

The plan is specific to the selected run mode. For example, a match-only run that reads an existing OSM snapshot advertises `osm.prepare` but omits `osm.download`, so an advertised `waiting` stage always represents work that can still execute.

The CLI resolves its inputs before selecting the plan. Local Swiss runs include `atlas.load`, cached products add `timetable.load`, and an explicit `--gtfs` adds `timetable.local_feed`. Generic GTFS runs also use `timetable.local_feed` around feed loading and route preparation. A full download run with an explicit local feed advertises both acquisition work and the local-feed preparation, each with its own lifecycle. Local reads can revisit ATLAS/timetable after acquisition; consumers must use states rather than phase position to infer completion.

Public progress reporting is scoped to the CLI invocation and resets even on failure. Normal library calls do not emit versioned public progress; existing internal timing diagnostics remain independent. Tests and custom runners can opt in with `progress_reporting()`.

The review application owns its database and publication substages. It combines its catalog with the engine plan without importing engine Python code.

The catalog intentionally merges implementation details that are not useful operational boundaries:

- the Overpass request and saving its XML response are one download step;
- GTFS scan, partition and trip-reduction internals are one timetable-pattern step;
- grouped, long-distance, local-reference and nearest-neighbour passes are one proximity step;
- distance, attribute, route-contradiction, unmatched and duplicate predicates are one problem-detection step;
- final match bookkeeping is described as identifying the remaining unmatched stops.

Algorithm documentation remains authoritative for the detailed predicate order.

## Event example

```json
{
  "event": "stage_started",
  "progress_schema_version": 1,
  "stage_id": "osm.download",
  "stage_spec": {
    "id": "osm.download",
    "parent_id": "osm",
    "phase": "osm",
    "label": "Download OSM data from Overpass",
    "description": "Request the Swiss public-transport snapshot and save the returned OSM XML.",
    "order": 10,
    "progress_kind": "indeterminate"
  }
}
```

Percentages are emitted only when a stage has a real `processed` and `total` count. Otherwise consumers show state and elapsed time. Cache hits use `stage_outcome` with `reused`; inapplicable work uses `skipped`.

Heartbeat emission stops before the terminal event. A stage failure includes its error text. Each selected stage executes once per CLI run; predicates sharing a public stage must be adjacent when reporting is enabled. Consumers should ignore delayed progress after completion and close active stages when a process dies without emitting a final event. A process may emit internal unversioned JSON as well; it is not part of this protocol.

## Adding or changing a stage

1. Prefer an existing public substage when the new work is an implementation detail of the same user-visible outcome.
2. If a new operational boundary is justified, add one catalog entry with a new stable ID.
3. Wrap the work with `progress_stage(stage_id)`. Generic predicate runners should assign metadata rather than embedding presentation code in algorithms.
4. Add catalog and lifecycle tests. Do not assert wall-clock values or heartbeat counts.
5. Update this reference. IDs must not be renamed within schema version 1; label and description improvements are compatible.

Progress tests execute tiny Swiss, explicit-GTFS and generic GTFS CLI runs, verify that their advertised stages all resolve exactly once, and validate the result bundles. Acquisition tests assert emitted outcomes alongside actual cold/warm cache reuse, corrupt-cache rebuilding and failure recovery. Full CLI tests cover cold and warm downloads, including an explicit local-feed override. Matching correctness remains independently tested; progress tests do not assert private timing spans or heartbeat counts.
