# E4 Problems

After matching, the engine looks for data-quality problems in both datasets: matched stops that are far apart, stops without a counterpart, conflicting attributes, duplicates and matches that contradict the route evidence. Each problem has a type and a priority, so reviewers can start with what matters most. This chapter explains how problems are detected and prioritized; [A2.4](https://github.com/openTdataCH/stop_sync_osm_atlas/blob/main/documentation/2.4%20Problems%20Page.md) shows how reviewers browse them.

## Problem categories

| Category | Asks | Typical fix | Status |
|---|---|---|---|
| [Stop problems](4.1%20Stop%20Problems.md) | Is this stop in the right place, with the right attributes? | Move a node, correct tags, report an ATLAS issue | Implemented |
| [Route entity problems](4.2%20Route%20Entity%20Problems.md) | Does this route exist on both sides, with the same attributes? | Create or delete a route relation, fix its tags | Planned |
| [Route membership problems](4.3%20Route%20Membership%20Problems.md) | Does the route serve the same stops in the same order? | Add, remove or reorder relation members, fix roles | Planned |

Only stop problems are detected today. Route comparison results ([E3](3.%20Routes.md)) are exported, but no route-level problems are derived from them yet.

## Priorities

| Priority | Meaning |
|---|---|
| **P1** | Critical: a large discrepancy, such as a match more than 80 m apart, or a missing counterpart |
| **P2** | Significant: a moderate discrepancy that needs attention |
| **P3** | Minor: a small discrepancy, worth checking |

Priorities follow fixed rules: distance thresholds from the [dataset profile](2.%20Matching%20process.md#dataset-profiles), exemptions for operators with large stations (`SBB` in the Swiss profile), the importance of the attribute that differs, and whether a counterpart exists nearby. [E4.1](4.1%20Stop%20Problems.md) lists them.

## How detection works

Problem detection uses the same records as matching; no database or object mapping is involved. `ProblemContext.build()` first indexes the complete `MatchingOutput` once: spatial trees, counts per UIC number, duplicate groups and route evidence. Every problem rule is then a plain function:

```python
def rule(ctx: ProblemContext, record: MatchRecord | SourceStop | OsmNode) -> list[ProblemResult]
```

Each rule decides from the record's type whether it applies, and returns an empty list otherwise:

| Rule | Applies to |
|---|---|
| `distance_problem`, `attributes_problem`, `contradicts_route_matching_problem` | Matches (`MatchRecord`) |
| `unmatched_problem` | Unmatched source stops and OSM elements |
| `duplicates_problem` | All three |

The list of rules, `STOP_PROBLEM_PIPELINE`, therefore serves matched and unmatched records alike:

| Records | Evaluated by |
|---|---|
| Matches | `MatchRecord.evaluate_matched_problems(ctx, STOP_PROBLEM_PIPELINE)` in `api.py` |
| Unmatched entities | A loop over `STOP_PROBLEM_PIPELINE` in `api.py`, which also records the distance to the nearest counterpart as evidence |

Effectively matched trio middles are not evaluated as unmatched. External callers can use `evaluate_unmatched_problems()` for the same contract.

Every rule returns `ProblemResult` values:

```python
@dataclass(frozen=True)
class ProblemResult:
    problem_type: str   # distance, attributes, contradicts_route_matching, unmatched, duplicates
    priority: int       # 1 = P1, 2 = P2, 3 = P3
    has_source_duplicate: bool = False
    has_osm_duplicate: bool = False
```

The engine exports each problem with a stable `problem_id`, derived from its type and the keys of the affected entities, plus its priority and evidence ([result bundle format](Result%20bundle%20format.md#problems)). The review application stores the exported type and priority; it never re-evaluates the rules.
